## 2. 本机 Docker/WSL 故障：根因与修复记录（2026-09-12）

### 2.1 现象

1. Docker 客户端 29.7.2 正常，但引擎连不上：`failed to connect to the docker API at npipe:////./pipe/dockerDesktopLinuxEngine`。
2. `wsl --status` 报：**"WSL2 无法启动，因为此计算机上未启用虚拟化"**（实际 BIOS VT-x 是开的）。
3. 启用"虚拟机平台"功能后第一次重启，出现**"撤销刚才的更改"**回滚画面——这不是新问题，用户此前在安装 vim、DevEco Studio 时期也多次见过同一画面。

### 2.2 证据链（故障定位过程）

| 检查 | 结果 | 结论 |
|---|---|---|
| Setup 事件日志（2026-09-12 11:22:14） | `Update VirtualMachinePlatform ... failed to be turned on. Status: 0x800f0922` | 功能启用失败，重启时整体回滚 |
| System 事件日志（11:22:01，同一分钟） | `VMSP service failed to start: Insufficient system resources` | 虚拟机平台服务起不来 → 触发回滚 |
| `Get-ComputerInfo` | `HyperVisorPresent: False`，`VirtualizationFirmwareEnabled: True` | 固件虚拟化正常，但 hypervisor 从未启动 |
| `bcdedit /enum {current}` | **没有 `hypervisorlaunchtype` 这一行**（只有 `vsmlaunchtype Auto`） | 启动配置里 hypervisor 从未被设为自启 |
| `DISM /Online /Cleanup-Image /CheckHealth` | **"The component store is repairable."** | WinSxS 组件库损坏（可修复）——总根因 |
| Windows 更新历史 | 月度累积更新（KB5124008 等）均成功 | 更新通道健康，损坏是区域性的 |
| 其他排除项 | 无 WSUS 策略；AV 仅 Defender + 微软电脑管家；C 盘余 38.8 GB；16 GB RAM；无 pending.xml 残留 | 干扰项全部排除 |

**根因（两条叠加）**：
1. **WinSxS 组件库损坏**：所有触碰损坏区的服务事务（启用功能、安装更新/驱动）在重启应用阶段失败并整体回滚——这就是"撤销刚才的更改"反复出现的机制，历史上 vim / DevEco 时期的同类画面同源（失败的是当时的系统组件操作，与那些软件本身无关）。
2. **BCD 缺 `hypervisorlaunchtype`**：hypervisor 从不启动，任何依赖它的启用操作（VMSP）必然失败，即使组件库健康也会卡在这一步。

### 2.3 已执行的修复（全部验证通过，按序）

```text
1. bcdedit /set {current} hypervisorlaunchtype auto      → 操作成功
2. DISM /Online /English /Cleanup-Image /RestoreHealth   → "restore operation completed successfully"（约 25 分钟）
3. sfc /scannow                                          → 复核阶段 "Repairing 0 components"，无需再修
4. DISM /Online /English /Cleanup-Image /CheckHealth     → "No component store corruption detected"（修复前是 repairable）
5. DISM /Online /English /Enable-Feature /FeatureName:VirtualMachinePlatform /NoRestart
                                                          → State: Enabled，RestartNeeded: False（无挂起事务）
```

### 2.4 遗留动作（重启后按序验证）

组件库已修复、功能已在运行时完整提交（无待应用事务，故下次重启**不会再出现回滚画面**；`hypervisorlaunchtype auto` 也需重启才生效）。重启后：

```text
1. 验证 hypervisor 已启动：PowerShell (Get-ComputerInfo -Property HyperVisorPresent).HyperVisorPresent 应为 True
2. 启动 Docker Desktop，等引擎就绪
3. docker pull python:3.11-slim
4. 冒烟（与 DockerSandboxExecutor 的加固参数一致）：
   docker run --rm --network none --read-only --user 1000:1000 python:3.11-slim python -c "print('ok')"
```

通过后即可对 P2-E 的 `DockerSandboxExecutor` 做真容器验证（其构造函数会自动探测 `docker_available()`）。**万一仍失败**（证据上无此迹象），升级手段为安装介质修复安装（in-place repair）。

## 3. 下一个任务 P2-F：可选 OpenTelemetry + 脱敏（开工方案）

> 详细方案同见 `docs/HANDOFF_2026-09-09.md` 第 6 节；此处为独立摘要。

**目标**：第三条观测轨道。环境未装 OpenTelemetry 时必须零影响（no-op）；默认不把 prompt/工具参数写进遥测。

1. `pyproject.toml` 增 `[project.optional-dependencies] telemetry = ["opentelemetry-api", "opentelemetry-sdk"]`。开发机**不必安装**，测试全程走 no-op / 假 tracer。
2. 新增 `miniclaw/telemetry/tracing.py`：`try-import` 得 `HAS_OTEL`；`TracingListener`（on_event 适配器）把事件映射为 span——RUN_STARTED→根 span、MODEL_REQUESTED→子 span(step)、TOOL_CALLED/TOOL_RETURNED→工具 span（attributes 默认仅 name/call_id/ok/error_kind 等非负载字段）、RUN_FAILED→记 error；`HAS_OTEL=False` 时 `make_tracing_listener()` 返回 no-op，不抛错。
3. 脱敏：`make_tracing_listener(..., include_payloads=False)` 默认；True 时工具 arguments/content 仍默认脱敏（键集语义与 EventStore `_REDACTED_KEYS` 对齐），prompt 类字段永不导出。
4. `build_runtime(..., tracing_listener=None)` 并入 combined listeners（factory 已是列表拼接）。
5. 测试 `tests/test_telemetry.py`：HAS_OTEL=False no-op 不落任何东西；假 tracer 断言 span 序列与事件流对齐、默认无 arguments/content；全量回归（148 + 新增）后提交 `feat(phase2): optional opentelemetry tracing`。

**关键契约提醒**（P2-F 会触碰 factory/listener，改前自查 `HANDOFF_2026-09-09.md` 第 4 节）：Runtime 无状态、单一组装入口 `build_runtime`、三键隔离、增量持久化；新增 dataclass 字段一律放最后带默认值。
